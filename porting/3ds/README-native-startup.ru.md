# DS Startup Test 0.1.0

**Последующий аппаратный результат: FAIL.** Пользователь сообщил о прежних чёрных экранах/зависании и подтвердил отсутствие `SD:/3ds/ds-native-startup-v0.1.0/`. Уменьшение куч до2+2MiB не устранило симптом. Повторно не запускать; отсутствующие логи не запрашиваются. [Разбор](../analysis/native-startup-hardware-fail-v0.1.0/report.ru.md), [аппаратная запись](../analysis/hardware/native-startup-v0.1.0-user-result.json). Инструкция ниже сохранена как описание подготовленного теста, не разрешение на повторный запуск.

Отдельная проверка раннего запуска после аппаратного FAIL DS Native Game h2. Собрана и проверена в Azahar; затем пользователь сообщил об аппаратном FAIL, указанном выше. Это startup-only CIA: оригинальный движок, ресурсы игры, DS34/Citro3D и команды PICA в неё не входят. Для текста на LCD используются стандартные libctru gfx/console и GSP display.

## Файл и конфигурация

- CIA: [build-native-startup-v0.1.0/startup.cia](build-native-startup-v0.1.0/startup.cia), **146880 bytes**.
- Название в HOME: **DS Startup Test 0.1.0**.
- Отдельный Title ID: **000400000FDE7200**, product code `CTR-H-DSST`.
- SHA256: `4ae98b7dd2f59df827b9e3f5ad966e4abe2896db538c65be3bf18832ac27fa7c`.
- Normal heap **2 MiB**, linear heap **2 MiB**, main stack **256 KiB**.
- Профиль сохранён от h2: `SystemMode: 64MB`, **`SystemModeExt: 178MB`**, kernel **2.44**. Режим памяти одновременно с кучами не меняется.

До стандартного SDK-аллокатора небольшая обёртка читает фактические `RESLIMIT_COMMIT limit/current`, затем вызывает оригинальный `__system_allocateHeaps` и повторяет измерение. В ней нет malloc/stdio/SD. Проверено по дизассемблеру связанного ELF. Сам аллокатор libctru не изменён.

## Ожидаемая проверка после отдельного согласования

1. Поместить только `startup.cia`, например в `SD:/cias/`, и установить обычным CIA installer на New 3DS. Игровые файлы, APK и `.so` не нужны. Старую игровую CIA этот Title ID не заменяет.
2. Открыть **DS Startup Test 0.1.0**. Ничего не нажимать для начала: ожидается нижний экран **MAIN REACHED / READY - START exits** и значения limit/committed/available/heap delta. Верхний экран пустой — так задумано.
3. После фиксации экрана нажать **START один раз**. Ожидается обычный возврат в HOME. A не запускает ничего.
4. Если создавались логи, скопировать целиком новый `SD:/3ds/ds-native-startup-v0.1.0/run-NNNN/`: `ready.txt`, `result.json`, `exit.txt`. Папка теста отделена от всех прежних диагностик; существующие run пропускаются. При недоступном SD экран сообщает об этом, START остаётся доступным.

READY выводится и его framebuffer flush выполняется до необязательной записи SD. `exit.txt` означает только намерение вернуть управление из main: фактический возврат в HOME проверяется отдельно. При чёрных экранах или отсутствии возврата результат — FAIL/неизвестная стадия; повторный запуск этим документом не разрешается. Нельзя гарантировать достижение main на ещё не проверенной аппаратной конфигурации.

## Что уже проверено программно

Три последовательных цикла **payload, извлечённого из этой CIA**, в одном Azahar core с одной SD: main/READY, START, освобождение GSP и обеих куч до host unload. Новых ошибок unmapped/exception/assertion не найдено. Во всех циклах:

| Измерение до/после SDK-куч | Bytes |
|---|---:|
| Commit limit | 186646528 (178 MiB) |
| Commit до куч | 409600 (400 KiB) |
| Доступно до куч | 186236928 |
| Добавили обе кучи | 4194304 (4 MiB) |

Это измерения эмулятора, а не приставки. Игровой frame/baseline/safe_exit донорских потоков этим тестом не проверяются и не изменяются.

## Как трактовать будущий аппаратный результат

- READY и возврат в HOME подтвердят работоспособность малого startup в профиле 178 MiB. Сами по себе они **не докажут**, что причиной FAIL h2 были большие кучи: у минимального executable меньше статическая память и отсутствуют игровые зависимости.
- Измеренный limit 64/124 MiB несовместим с запросом h2 172 MiB. При limit 178 MiB нужно учитывать его собственный code/BSS/stack и все дополнительные charges; нельзя прямо подставить current малого теста вместо current h2.
- Если бюджет h2 достаточен, остаются возможными отказ большого linear allocation, ранние службы, gfx/console и SD. Если малый тест тоже остаётся чёрным, гипотеза «только размер куч» не подтверждается.
