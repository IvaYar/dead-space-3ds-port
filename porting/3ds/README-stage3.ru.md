# Dead Space для New 3DS — этап 3

Версия **0.3.0**, приложение **DS Loader Test 3**. Проверяется начальный обмен с JNI: выполнение настоящего `JNI_OnLoad` и двух строковых обёрток игровой библиотеки. Меню, игровой процесс, графика и звук пока не реализованы.

**Аппаратный результат получен:** пользователь прислал полный `STAGE 3 PASSED` с `Luma3DS native RX`. Возврат `JNI_OnLoad`, сохранение JavaVM, строковые callbacks и освобождение строки подтвердились. Журнал: `analysis/hardware/stage3-v0.3.0-user.log`.

## Запуск на твоей консоли

Этап 2 версии 0.2.2 уже прошёл на твоей New 3DS с Luma3DS 13.3.3. Его журнал сохранён в `analysis/hardware/stage2-v0.2.2-user.log`. Механизм подготовки RX-страниц и работы с кэшем перенесён в этап 3 без изменений. JNI-код этапа 3 также прошёл на устройстве.

1. Скопируй `deadspace-loader-stage3-v0.3.0.cia` в свою папку `/CIA/` на SD-карте и установи через FBI.
2. Открой **DS Loader Test 3** из HOME Menu. Это отдельное приложение с Title ID `000400000FDE5200`; первые два теста удалять не требуется.
3. На экране **`STAGE 3 READY - press A`** нажми **A** для запуска. **START** выходит без запуска проверки.
4. Ожидаемый итог — **`STAGE 3 PASSED`**. Нажми **START** и пришли журнал **`/3ds/deadspace/stage3-v0.3.0-log.txt`**.

Библиотека `/3ds/deadspace/libEAMGameDeadSpace_orig.so` остаётся от этапа 2. Копировать её повторно не требуется. Ресурсы игры для этой проверки пока не нужны: путь к ним используется только как тестовая строка.

Полный архив `deadspace-3ds-stage3-v0.3.0-local.zip` также содержит библиотеку, 3DSX и отчёты. Если используешь архив, скопируй **содержимое** папки `SD_CARD` в корень карты, затем установи `/CIA/deadspace-loader-stage3.cia`. Саму папку `SD_CARD` на карту переносить не нужно.

При `STAGE 3 STOPPED` пришли новый журнал. Он закрывается на контрольных точках перед продолжением. Для повторного запуска служит A, если восстановление RW-прав прошло успешно. При ошибке восстановления память сохраняется до завершения приложения, а повторный запуск блокируется.

## Что выполняется

Загружается тот же донор 1.1.33 SD, SHA-256 `dd42272365d0abd8ad9c89450bb7f869ee4ac0ad548525758e6a1e7df4d3c1eb`. Размер и CRC проверяются до подготовки образа.

До выполнения проверяются точные инструкции функций как в ELF, так и в памяти, размеры экспортов, исполняемые сегменты, адрес GOT и соответствующий слот в доступном для записи сегменте. В этой версии донора `JNI_OnLoad` сохраняет переданный указатель JavaVM и возвращает `0x00010004`; других функций он не вызывает. В ARM-тесте проверено, что после вызова изменились только четыре байта ожидаемого слота образа.

Затем создаётся строка `sdmc:/3ds/deadspace/assets/published/`. Настоящие C++-обёртки игры `GetStringUTFChars` и `ReleaseStringUTFChars` вызывают обработчики приложения через таблицу JNI. Проверяются совпадение байтов, счётчики вызовов и освобождение строки.

Реализован ограниченный однопоточный набор JNI: `GetVersion`, `DeleteLocalRef`, `NewStringUTF`, `GetStringUTFLength`, `GetStringUTFChars`, `ReleaseStringUTFChars`, `GetJavaVM` и `JavaVM.GetEnv`. Таблицы используют индексы из спецификации [JNI functions](https://docs.oracle.com/javase/8/docs/technotes/guides/jni/spec/functions.html) и [Invocation API](https://docs.oracle.com/javase/8/docs/technotes/guides/jni/spec/invocation.html). Вызовы имеют ARM AAPCS, совместимый с проверяемыми обёртками Android.

Это начальный набор, а не JVM: отсутствуют классы, вызовы Java-методов, исключения и подключение потоков. Остальные слоты таблиц равны NULL. Пул содержит восемь строк до 255 байт каждая, хранит байты Modified UTF-8 без преобразования в UTF-16 и запрещает удаление строки с активным заимствованием байтов. Такой набор ещё нельзя передавать произвольным функциям движка.

209 конструкторов, точка входа движка и другие JNI-экспорты не вызываются. Внешние импорты игровой библиотеки пока не привязываются; проверяемые пути к ним не обращаются. Полноценный запуск потребует реализации системных функций Android, потоков, файлового ввода, графики, звука и управления.

## Проверки и воспроизведение

```powershell
python porting/tools/package_stage3.py
```

Перед упаковкой выполняются 14 регрессионных проверок ARM ELF-загрузчика, 14 проверок JNI и ограниченных путей оригинального кода в Unicorn, проверка структуры и хешей CIA через ctrtool, а также восемь сценариев Azahar для 3DSX и исполняемого содержимого CIA: READY без A, отсутствующая библиотека, изменённая библиотека и успешная проверка.

В Azahar используется явно обозначенная ветка `emulator (RX not tested)`. Она не проверяет настоящие права исполнения и кэш ARM11. Для механизма RX получены аппаратные результаты этапа 2 версии 0.2.2 и этапа 3 версии 0.3.0. Отчёты и снимки находятся в `validation/`, контрольные суммы файлов — в `build-manifest.json`.

Исходники: `main_stage3.c`, `ds_jni.c`, `ds_bootstrap.c`, общий загрузчик `ds_elf.c` и неизменённые после этапа 2 версии 0.2.2 `ds_exec.c`, `ds_cache.s`.
