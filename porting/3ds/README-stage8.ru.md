## Установка

Если `/3ds/deadspace/libEAMGameDeadSpace_orig.so` осталась от предыдущего теста, достаточно нового CIA. Ресурсы игры для этой проверки не нужны.

1. Скопируй `deadspace-loader-stage8-v0.8.0.cia` в папку `/CIA/` на карте и установи через FBI.
2. Запусти **DS Loader Test 8** из HOME Menu. Title ID — `000400000FDE5700`; предыдущие тесты можно оставить.
3. На экране `STAGE 8 READY - press A` нажми **A**.
4. Ожидается **`STAGE 8 PASSED`**. Выйди через START и пришли `/3ds/deadspace/stage8-v0.8.0-log.txt`.

При STOPPED тоже нужен журнал. После штатной очистки A запускает проверку повторно. Если поток не завершился, осталась незавершённая инициализация C++ или не восстановились права памяти, повтор блокируется до выхода.

Полный архив `deadspace-3ds-stage8-v0.8.0-local.zip` содержит CIA, 3DSX, библиотеку и отчёты. Копируется **содержимое** `SD_CARD` в корень карты, затем устанавливается `/CIA/deadspace-loader-stage8.cia`.

## Что проверяется

Собственный модуль компилируется C++-компилятором в ARM softfp без исключений и стандартной библиотеки C++. Запускаются его настоящий `DT_INIT` и функция из `.init_array`, созданная компилятором для двух глобальных объектов. Сначала записывается маркер 9, затем конструкторы объектов 1 и 2: ожидается порядок **912**. Повторный запуск плана отклоняется.

Два потока обращаются к одному локальному static-объекту. Первый задерживается внутри конструктора, второй обязательно успевает начать ожидание занятого guard. После разрешения первый завершает объект, второй получает уже готовый. Суммарно существует три объекта, порядок **9123**. Каждый объект выделяет память через ранее проверенный мост.

Реализованы ARM `__cxa_guard_acquire/release/abort` с четырёхбайтовым guard и признаком готовности в младшем бите. Отмена позволяет повторную попытку; release публикует готовый объект и будит ожидающих. Отдельно проверяется сохранение остальных битов guard.

`__aeabi_atexit` и `__cxa_atexit` учитывают разный порядок аргументов. Реестр вызывает деструкторы в обратном порядке, поддерживает выбор DSO, повторный finalize без двойного вызова, регистрацию новых callbacks и вложенный finalize из деструктора. Callback выполняется без удержания общей блокировки. Шесть вызовов проверяют фильтрацию и вложенность; затем при выгрузке ожидается уничтожение трёх объектов в порядке **321**.

Сначала полностью завершаются потоки, затем вызываются деструкторы, очищаются адаптеры и heap, восстанавливаются права памяти и освобождается код. При незавершённом потоке деструкторы не вызываются, модуль и его память сохраняются до выхода приложения.

## Проверка конструкторов и ограничений

`ds_init_bind_plan` работает после `ds_elf_prepare` и выполняет полную привязку импортов один раз. До запуска любого конструктора проверяются **все** адреса: допустимое выравнивание ARM/Thumb, принадлежность загруженному модулю и исполняемому участку с байтами в файле. Затем сохраняется копия адресов. Нулевые элементы и `0xffffffff` пропускаются. DT_INIT вызывается перед `.init_array`. Повторный и вложенный запуск готового плана отклоняются.

Оригинальные 209 конструкторов игры не вызываются: остаются 239 обязательных импортов. Попытка сформировать план для игры должна остановиться на отсутствующих привязках без изменения образа. Добавлены четыре импорта донора; общее число 149. Общий реестр — 156 записей: дополнительные API и диагностические helpers не увеличивают число поддержанных импортов игры.

Лимиты этой диагностики: 64 одновременно инициализируемых static-объекта, 256 зарегистрированных деструкторов и 256 элементов плана конструкторов. Завершённые guard не занимают слот. Переполнение реестра возвращает ошибку; неверное владение guard, рекурсивная инициализация того же объекта и исчерпание активных guard останавливают процесс, поскольку guard API не предусматривает возврат ошибки вместо конструктора. Нормальная проверка эти ошибки не вызывает.

Исключения C++, unwinding и RTTI-переходы через Android/native границу не реализованы. `__cxa_begin_cleanup`, `__cxa_call_unexpected`, `__cxa_type_match` и `__gnu_Unwind_Find_exidx` остаются непривязанными. Это ещё не разрешение запускать произвольные конструкторы движка. Ограничения прежних адаптеров также сохраняются.

## Локальная проверка и сборка

108 ARM-проверок: 84 прежние проверки загрузчика/ABI/runtime и 24 проверки C++/плана конструкторов. Отдельный C-модуль воспроизводит импортируемый `__dso_handle`, как у старой библиотеки игры; современный C++-компилятор создаёт собственный скрытый токен DSO.

В Azahar проверяются CIA/CXI и 3DSX: экран ожидания, отсутствующий и повреждённый донор, успешный запуск и повтор в одном процессе. Два дополнительных CXI проверяют повреждённый адрес последнего конструктора и незавершившийся поток. Эти сборки **не включаются в пакет для консоли**. Повреждённый адрес запрещает запуск даже предшествующего DT_INIT; при живом потоке код и реестр деструкторов сохраняются. Всего 12 сценариев.

CIA проверяется ctrtool: структура, Title ID, хэши секций и прежняя точная последовательность SVC 0x94. Исходники механизма RX/кэша совпадают с прошедшим аппаратную проверку этапом 7. Эмулятор не подтверждает native RX и I-cache; после локальных проверок этап 8 также успешно проверен на консоли пользователем.

```powershell
python porting/tools/package_stage8.py
```

Адреса и SHA-256 сохранённых копий — `analysis/android-abi/stage8-sources.json`. Реализация написана в этом проекте.
