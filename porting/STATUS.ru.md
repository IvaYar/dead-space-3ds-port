# Dead Space Mobile → New Nintendo 3DS: состояние работы

Дата: 28 октября 2026 года. Целевая платформа уточнена пользователем: семейство New Nintendo 3DS.

**Текущая точка:** [туман и texture combiners после рабочего меню](SCENE-RENDERER.ru.md), **511 core ARM-тестов**. В Azahar178MiB/CPU400 работают Normal/Easy и подтверждение, оригинальные вызовы прошли DS30/31. На2604-м кадре следующая остановка — `glLightModelfv`, caller00325e84; GL0, arena/paging failures0. Полного3D-кадра ещё нет. Донор английский1.1.33, перевод отложен. Новая CIA, gameplay/audio и аппаратная проверка новых адаптеров пока отсутствуют. Актуальная сводка — [menu-result.json](analysis/menu-result.json). Далее сохранена история прежних результатов.

**Самый новый результат:** [касания и приватные файлы](INPUT-SAVES.ru.md), завершены240 кадров Azahar на CPU100%. Оригинальные DOWN/UP вернулись, native descriptor write/read/reopen/append/EXCL/fstat пройден, игра создала приватные settings/statistics files. Прошли368 core ARM-тестов,9 штатных engine-сценариев,3 CPU audits и отдельные проверки снимков;14 isolated sensor-тестов сохраняют собственные свидетельства. Меню остаётся неподтверждённым: виден headphones screen. Следующий конкретный пробел — правильный APK AssetManager namespace, т.к. EAMCore.ini действительно есть в APK. Native memory124MiB, arenas20+80MiB, GL99 opt-in; аппаратный RX/cache прежний. CIA нет, продолжение локальное, GitHub — только по новому запросу. Ниже история предыдущих шагов.

**Последний локальный результат:** opt-in JNI-мост датчика прошёл прежнюю остановку; Unicorn и Azahar дошли до `glGetIntegerv(GL_VIEWPORT)`. Графического кадра нет. Прошли 166 core-тестов, 14 sensor-тестов и восемь engine-сценариев плюс отдельная HID-проверка. Подробности — [SENSOR-JNI.ru.md](SENSOR-JNI.ru.md). **Новое:** изолированный HID-мост акселерометра прошёл 12 ARM-тестов и отдельный Azahar CXI с 40 показаниями и штатным выключением. Он ещё не связан с JNI игры; прежняя остановка запуска сохранена. См. [SENSOR-BACKEND.ru.md](SENSOR-BACKEND.ru.md).

**Текущий результат на компьютере:** в Azahar и Unicorn прошли 209 конструкторов, JNI_OnLoad, создание приложения/поверхности, настоящая EAIO_Startup и системные свойства. Первый `NativeOnDrawFrame` вернулся; на втором стоит ранний отказ перед отсутствующим адаптером акселерометра. Изображения игры пока нет. Прошли 158 ARM-тестов и семь сценариев Azahar; 120 повторных callback без готового кеша не исчерпывают ссылки. Подробности — [PLATFORM-BOOTSTRAP.ru.md](PLATFORM-BOOTSTRAP.ru.md). Промежуточные блоки проверяются на компьютере; карту и установленный CIA сейчас менять не нужно.

## Что есть в этой папке

- `tools/inspect_packages.py` — анализатор APK и вложенных архивов на Python 3, без сторонних зависимостей. Не запускает код игры.
- `3ds/` — исходники диагностики ELF-загрузчика и конфигурация упаковки CIA.
- `tests/` — проверки ARM-кода и запуск диагностики в эмуляторе.
- `tools/package_stage1.py` — сборка, проверки и создание локального пакета первого этапа.
- `toolchain/` — локальные инструменты сборки с перечнями версий и SHA-256.
- `dist/` — собранные артефакты для проверки на консоли.
- `analysis/packages.json` — результаты проверки пяти APK: контрольные суммы, ELF-архитектура, зависимости, импортируемые функции, JNI-экспорты и состав ресурсов.
- `analysis/candidate-sd/libEAMGameDeadSpace_orig.so` — оригинальная игровая библиотека из модифицированного SD APK, извлечённая для исследования.
- `analysis/candidate-sd/assets/published/` — ресурсы SD-варианта для исследования. Они пока не преобразованы для 3DS.
- `reference/deadspace-vita/` — неизменённая копия открытого загрузчика для PS Vita, исходный commit `3eaa3c4b8a0201eec746f7676e0bddcffc5d5638`. Подмодули не загружены. Это сторонний проект под MIT, его лицензия сохранена внутри папки.

Исходные два архива не изменялись. Извлечённые игровые файлы остаются локально.

## Результаты проверки

В `DeadSpace-1.1.33-Universal.zip` находятся четыре APK. Вместе с отдельным `Dead-Space-v1-2-0-rus.apk` проверены пять вариантов. Исходники игрового движка в проверенных пакетах не обнаружены; присутствуют скомпилированные библиотеки и данные.

| Вариант | Игровая библиотека | SHA-1 игровой библиотеки |
| --- | --- | --- |
| 1.2.0 rus | `lib/armeabi/libDeadSpace.so` | `49ca4216896a02f7f562bd4f34ba5590bc966b00` |
| 1.1.33 HD | `lib/armeabi/libEAMGameDeadSpace_orig.so` | `922e3935d163d29a859f5d817007da703f45a981` |
| 1.1.33 SD | `lib/armeabi/libEAMGameDeadSpace_orig.so` | `3c4a1b844eddbf3b9f0d2d946433bc429cc64b2e` |
| 1.1.33 UD | `lib/armeabi/libEAMGameDeadSpace_orig.so` | `c3be777038ec4b76281ac91e6d8fafd84cbdf188` |
| 1.1.33 UD Arm64 | `assets/game/libDeadSpace32.so` | `c3be777038ec4b76281ac91e6d8fafd84cbdf188` |

HD/SD/UD APK дополнительно содержат маленькую библиотеку `libEAMGameDeadSpace.so` размером 4396 байт. Её нельзя принимать за сам игровой движок: основной код находится в файле с суффиксом `_orig.so`.

Arm64-вариант содержит оболочку AArch64 и вложенный 32-битный движок. Использовать его оболочку для 3DS оснований нет.

Проверенные 32-битные игровые библиотеки зависят от `libc.so`, `libstdc++.so`, `libm.so`, `liblog.so`, `libGLESv1_CM.so`. Для 1.1.33 таблица содержит 392 уникальных неопределённых динамических символа, в том числе 190 графических; у версии 1.2.0 — 398. Наличие символа в таблице не доказывает, что он используется на каждом пути исполнения.

Импортируются функции фиксированного конвейера OpenGL ES 1.x, включая матрицы, освещение, массивы вершин, сжатые текстуры и расширения OES. Здесь нет оснований утверждать, что основная проблема — обязательная поддержка GLES 2.0.

В метаданных `.ARM.attributes` записана архитектура v5TE. Это не полная проверка всех инструкций библиотеки и не гарантия совместимости с ARM11: отдельно нужны проверка машинного кода, операций VFP и соглашений вызова.

Для первого исследования выбран **1.1.33 SD**, поскольку это вариант с SD-ресурсами. Его вложенный архив содержит 1728 файлов общим размером 414822611 байт. Это размер данных на диске, а не измеренное потребление ОЗУ. Производительность и пиковая память не измерялись.

## Что даёт существующий порт для Vita

Проект [deadspace-vita](https://github.com/v-atamanenko/deadspace-vita) запускает закрытую игровую библиотеку через специально реализованное окружение Android. Поэтому отсутствие исходников игры само по себе не доказывает невозможность порта.

Однако Vita-загрузчик использует VitaSDK, VitaGL/PVR, kubridge и системные функции `sce*`. Они требуют замены на реализации для 3DS. Его текущая конфигурация также резервирует 250 MiB под newlib heap; это настройка Vita-проекта, а не измеренный минимальный объём памяти игры.

README загрузчика требует SHA-1 `0ed42b611415015807f759ec9b5457857143ce39` для оригинальной Xperia Play библиотеки. **Ни одна игровая библиотека из предоставленных пакетов не совпала с этим хешем.** Это означает, что готовность существующих патчей к этим модификациям не подтверждена. Обход проверки хеша не решает вопрос совместимости патчей.

## Что необходимо реализовать до игрового CIA

1. Локальный devkitARM/libctru/citro3d и инструменты упаковки настроены. Сборка выполняется через Python без make/cmake и без изменения системного PATH. Пользователь сообщил об успешной аппаратной проверке первого этапа.
2. Чтение ELF, загрузка сегментов и внутренние релокации реализованы. На втором этапе добавлена привязка внешних символов и подготовка исполняемых страниц через Luma. Выполнение тестового модуля, трёх константных функций донора, ABI float и управление RX/кэшем подтверждены на устройстве в версии 0.2.2. Конструкторы и игровой движок пока не вызываются.
3. Начальный JNI-набор подтверждён на устройстве на этапе 3, чтение ресурсов через Android ARM API — на этапе 4, память, строки и libm — на этапе 5, stdio/stat и базовые функции — на этапе 6, потоки/TLS и синхронизация — на этапе 7, статическая инициализация C++ — на этапе 8. На компьютере теперь проходят EAIO_Startup и чтение через выбранный набор JNI. Следующий блок — SystemAndroidDelegate и оставшиеся операции EAIO; также нужны синхронизация остальных адаптеров, зависимости Android и поддержка исключений. Нужно определить совместимость модифицированной библиотеки с патчами и точками входа Vita-порта.
4. Реализовать графический слой для реально вызываемых GLES 1.x функций и форматов текстур на PICA200. [citro3d](https://github.com/devkitPro/citro3d) предоставляет свой API. [c3dgl](https://github.com/SomeRandoLameo/c3dgl) может быть кандидатом для части функций, но автор помечает проект как ранний и не проверенный на настоящей консоли. Совместимость с этой игрой не установлена.
5. Перенести звук, ввод, сенсорные меню и сохранения. Для New 3DS исследовать управление камерой через C-stick; проверить читаемость интерфейса на экранах консоли.
6. Получить настоящее меню и игровой эпизод, измерить память/FPS, затем проверить уровни, бой, звук, сохранения и переходы между сценами на устройстве. После этого собрать и проверить CIA через makerom.

Неоконченные части этих пунктов описывают остающуюся разработку. Не подтверждены ни достижимость нужной скорости, ни полная проходимость игры на New 3DS. CIA первого этапа содержит диагностику, а не игровой рантайм.

Страница 4PDA по предоставленной ссылке дважды вернула HTTP 403 при попытке чтения. Содержимое темы и дополнительные версии с форума не проверены.

## Повторная проверка

Из корневой папки `Dead_space_mobile`:

```powershell
python porting/tools/inspect_packages.py
```

Команда повторно создаёт JSON-отчёт, не изменяя APK/ZIP. Опция `--extract-candidate` предназначена для первого извлечения в новую папку анализа; она откажется перезаписывать существующие файлы ресурсов. Для повторного извлечения можно указать другую папку через `--output`.

Анализатор успешно обработал все пять APK. Извлечение SD-ресурсов выполнено с проверкой CRC, которую обеспечивает чтение ZIP средствами Python. Это проверка архивов и инструментов подготовки, не тест запуска игры.
