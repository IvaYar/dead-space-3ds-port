# Close 0.1.3 hardware run-0001: выход после START retry подтверждён, автоматический выход ещё FAIL

01.11.2026. Получен один запуск настоящей New Nintendo 3DS и три фото в сообщении. После второго START пользователь подтвердил закрытие программы и возврат консоли к штатной работе. **Это подтверждение manual retry exit, а не успешного автоматического выхода и не HOME → X. Повторять текущую CIA ради данных не требуется.**

34 файла, 3 139 617 bytes, побайтно скопированы из `porting/ds-native-game-v0.1.3/run-0001/` в `analysis/hardware/native-game-close-v0.1.3-user-run-0001/`. SHA256 originals/archive совпадают; исходная папка не менялась. Фото доступны в сообщении; локального архивирования фотографий не заявляем. [Manifest](archive-manifest.json), [численный результат](hardware-result.json), [наблюдения пользователя](user-observations.json).

## Что произошло

1. A запустила оригинальную игру. Обе анимации (EA и наушники) прошли. Фото примерно через 3 минуты показывает FRAME FAIL / Cooperative shutdown running.
2. Все 600 callbacks вернулись. Frozen gate `ea733050` не получен, последний CRC `bf2a6bfd`. Автоматически началась очистка.
3. Поздний `Run0xb6e6c` продолжал IO. Первый bounded kernel wait закончился `completion=110`, `pumps=0`, **60069 ms**. На timeout шесть workers ещё живы; программа корректно сохранила ресурсы и перешла в STOPPED.
4. Пользователь сообщает: примерно через минуту после первого START видел STOPPED / cleanup incomplete. После второго START приложение закрылось. Журнал содержит одну зарегистрированную retry: `close_pending=0 home_pending=0 source=none`.
5. К началу retry loader **уже завершился в фоне**, kernel poll=0/done=1. Pause/Stop вернулись, jobs/audio/periodic завершились; очистка дошла до IO/JNI, GPU drain/Fini, exit marker и `PROCESS return`.

Минутные интервалы — приблизительная оценка пользователя. Они не являются точным временем отдельных фаз. У общего журнала нет wall-clock timestamp для каждой строки, поэтому нельзя вычислить точную полную длительность позднего loader или момент нажатий.

## Почему это другой timeout

При первом timeout snapshot показывает **sync state=0, busy byte=0, flag68=1**. Main delegate уже подтверждён; старого ожидания state1/flag68=0 в этой точке нет. Shutdown не выполнял delegate pump (`pumps=0`), поэтому аппаратная работа нового pump-пути этим запуском непосредственно не проверена.

IO progress идёт во всех двенадцати 5-секундных интервалах: на 5-й секунде reads=11302/bytes=25744113, на 60-й reads=19491/bytes=59000310. Между этими отметками прибавились **33 256 197 bytes**, около **0,58 МиБ/с** в учётчиках guest IO. Это скорость продвижения приложения с чтением, обработкой и планированием потоков, **не измерение физической пропускной способности SD**. Обвинять карту или GPU по этим данным нельзя.

Жёсткого 60-секундного бюджета оказалось мало для продолжающейся загрузки. Это не доказательство нового deadlock: после timeout поток продолжил работать и к retry вернулся сам. Увеличивать лимит без ограничений нельзя; следующий вариант должен автоматически давать ограниченное дополнительное время только при доказанном прогрессе, иметь общий hard deadline и сохранять FAIL при остановке прогресса.

START во время `native_drain_loaders` не опрашивается: там обслуживается APT, но HID проверяется уже в STOPPED. Первое нажатие могло прийти во время ожидания и не стать последующим `hidKeysDown`. Это объяснение по коду и сообщениям пользователя; в журнале нет отдельной трассы первого нажатия, поэтому его точный момент не установлен.

## Что подтверждено на устройстве

- `threads-after_quiesce.json`: все **6 workers done=1 и kernel_wait=0**.
- `threads-after_join.json`: **0 worker handles**, остаётся только main record.
- IO **174 opens / 174 closes**, active=0, directories=0; JNI cleanup=13.
- `SHUTDOWN live workers=0`, exit.txt присутствует; последующий `PROCESS return ... cleanup=complete attempts=2`.
- Итоговые `frame_status=FAIL`, `cleanup_status=complete`, `safe_exit=true`; frame failure не заменён PASS.
- Пользователь/третье фото подтверждают возврат в HOME без прежнего зависания закрытия. Отдельного аппаратного измерения освобождения heap нет: оно было проверено host-тестами Azahar, а здесь подтверждены kernel quiescence, гостевой порядок очистки и наблюдаемый возврат.

**HOME → X и POWER не описаны в этом запуске и не считаются проверенными.** `home_pending=false`, `close_pending=false`. Причин повторять старый аппаратный сценарий до исправления автоматического IO ожидания нет.

## Изображение и память

Девять raw/GX captures прошли независимую проверку CRC/readback и границ команд. Последний raw **побайтно равен аппаратному Stable 0.1.2**; расхождение со frozen software reference по-прежнему **9231 pixels**. Нового графического исправления/подмены baseline нет. [Локальный capture audit](capture-audit.json) остаётся private.

Normal allocator footprint — 19 222 528 bytes (около18,33 МиБ), commit126754816bytes; donor brk peak67112960bytes, mmap peak3919pages. Donor refusals/runtime failures=0, GL error/failed GPU submits=0. Получен аппаратный бюджет поздней загрузки до её завершения без установленного OOM; это не гарантия памяти будущей игровой сцены.

`threads-before_pause.json` перезаписан второй попыткой: в нём B уже done. Первую фазу подтверждают сохранённые `after_loader_wait` и `stopped_retained`. В следующей адресной диагностике snapshots нужно разделять по attempt, чтобы не терять историю.

На баннере HOME осталась надпись «EXPERIMENTAL0.1.0»: builder копировал старый `.bnr`. Экран приложения сообщает Close0.1.3, журнал и его namespace соответствуют новой реализации. Старая надпись не является доказательством запуска неправильной CIA. Hash установленной CIA независимо не измерялся; ожидаемый локальный кандидат SHA74f94904…fe3e0. Баннер нужно исправить при следующей подготовке пакета.

## Дальше

Сначала программно воспроизвести медленное, но продолжающееся late IO и проверить автоматическое ограниченное продолжение без START, отдельно отсутствие прогресса и hard deadline. Сохранить main delegate и все kernel/GPU lifetime guards, настоящий frame FAIL. Затем проверить HOME/X и подготовить один следующий кандидат, если проверки пройдут. До этого автоматический аппаратный exit gate остаётся закрытым; к управляемой сцене переходить рано.

Software proofs Close0.1.3 сохранены; их release gate до аппаратуры скопирован в [software-release-gate-before-hardware.json](software-release-gate-before-hardware.json). Текущий audit теперь учитывает hardware partial и не выдаёт новый ready=true поверх этих данных. В этом разборе нет новых сборок, эмуляторных/аппаратных запусков, изменений GPU/native-game/shutdown, очистки и push.
