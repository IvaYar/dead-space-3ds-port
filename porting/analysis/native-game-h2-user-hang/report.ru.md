**Последующее уточнение пользователя: «нет папки».** Диагностическая папка на SD не появилась. Отдельно root и конкретный run не различены; повторно просить отсутствующие файлы не нужно. Существующих hardware markers для локализации сейчас нет.

Машинная запись: `analysis/hardware/native-game-v0.1.0-h2-user-result.json`. Ожидается DS Native Game0.1.0 h2, TitleID000400000FDE7100, CIA SHA256 `90fb19919c1b132e30fed0936802375d2ccecfdbb7d9c504d5edbef131d35622`; установленный на устройстве файл отдельно не измерялся. Аппаратных логов этого запуска пока не получено. Не смешивать с прежними `porting/run-0001`, `run-0002`: это другие DS34 испытания.

## Что можно установить по исходникам

Проверен `tests/native_game.c`, в частности main и screen. Путь до намеренного A:

1. CRT/libctru startup: heap reservations40MiB normal/132MiB linear, services и main thread.
2. `gfxInitDefault()` → `consoleInit(GFX_BOTTOM,NULL)` → `RecursiveLock_Init`.
3. `make_folder()`: mkdir SD:/3ds, diagnostics root и нового run-NNNN.
4. Открытие `native-game.log`.
5. `screen(READY...)`: printf и `GSPGPU_FlushDataCache` нижнего framebuffer.
6. Запись/закрытие `ready.txt`.
7. `aptMainLoop()`/HID polling; только ветка `KEY_A` вызывает run → initialize → original donor/bootstrap/GPU backend.

Поэтому первым изучается **startup/CRT/heap/service/gfx/SD/первый экран**, а не повторно исправленный shader или shutdown6 workers. Причина пока не доказана. Чёрный экран сам по себе не говорит, какая из этих операций была достигнута, и не доказывает отсутствие выполнения main.

Отдельная неоднозначность ввода: h2 не ждёт отпускания кнопок перед активацией A. Если HID сообщает KEY_A на первом scan, текущий код сразу входит в run. Отсутствие *нового намеренного* нажатия A пользователем нельзя без лога превращать в доказательство того, что initialize ни разу не вызван. Это потенциальный механизм, а не установленная причина этого запуска. Сам gate/проверка отпускания кнопки в этой сессии не менялись.

## Какие данные нужны без повторного запуска

Пользователь уже сообщил об отсутствии папки **SD:/3ds/ds-native-game-v0.1.0/run-NNNN/**. Этот запрос закрыт отрицательным наблюдением; не просить новый запуск ради её создания. Таблица ниже сохраняет смысл возможных markers для будущего согласованного теста, а не утверждает наличие файлов в текущем испытании.

| Положительное наблюдение | Что оно подтверждает |
|---|---|
| Новый run-NNNN существует | Создание run-папки было достигнуто. |
| Есть новый native-game.log | Файл журнала был создан; пустой журнал **нормален до вызова initialize**, потому что первой строки startup до READY в h2 нет. |
| Есть полный ready.txt | Выполнены screen() и последующая запись marker; это ещё не доказательство входа в HID loop или видимости текста на LCD. |
| Есть STAGE preflight в новом журнале | Ветка run/initialize уже исполнялась; следует разбирать достигнутую стадию, даже если пользователь ещё не нажимал A намеренно. |
| Есть последующие STAGE/RX/constructors/GPU markers | Их последовательность сузит фактическую точку остановки. |

Отсутствие файла/последней строки слабее положительного marker: внезапное питание могло не сохранить последнюю запись. Никакая аппаратная причина, PICA submit/stall, RX verification или состояние donor threads пока не объявляются установленными.

## Проверено в уже собранном ELF: ранний memory/profile path

Без сборки/запуска прочитан disassembly существующего h2 `native-game.elf`. `__system_allocateHeaps` (`0x132188`) получает process resource limit и current usage, сравнивает доступный остаток с суммой двух запрошенных heap. У h2 это40MiB normal +132MiB linear = **172MiB**, резервируемые до main. При превышении лимита есть ветка `0x132308 → svcBreak`; при неуспехе normal/linear `svcControlMemory` также вызывается svcBreak. Следовательно, этот конкретный путь может остановить приложение **раньше console/SD logger**. Из отсутствия папки не следует, что именно он сработал.

Связанный `__appInit` (`0x132f2c`) вызывает srvInit, aptInit, hidInit, fsInit и archiveMountSdmc до пользовательского main. После них main всё ещё должен завершить gfxInitDefault/consoleInit и mkdir до первого журнала. Диагностическая папка не отделяет сбой резервирования памяти от service/gfx/mkdir failures и потери незаписанных данных при Power off.

Есть конкретное, ещё не проверенное аппаратно отличие: аппаратно успешный UV Mask использовал **SystemMode64MB / SystemModeExt Legacy / kernel release2.33**; h2 использует **SystemModeExt178MB / kernel release2.44** и явные большие heap. Не менять эти параметры одновременно в будущем тесте. Результат Azahar не измеряет реальный process resource limit New3DS пользователя. Ни недостаток памяти, ни несовместимость расширенного профиля здесь не доказаны.

Первые проверки теперь относятся к отсутствующему раннему startup evidence и этому memory/profile отличию. Возвращаться к UV masks/PICA или6 donor shutdown без новых markers оснований нет. Возможный будущий startup-only тест должен оставлять профиль/лимиты явно проверяемыми и получать отдельное разрешение на железо; новой CIA для него пока нет.
