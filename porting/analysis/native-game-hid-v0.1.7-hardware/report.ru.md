# Аппаратный HID 0.1.7: оригинальная навигация и подтверждение A прошли

Принят один пользовательский `run-0001` на настоящей New Nintendo 3DS. **Физический D-pad работает, оригинальный движок переключает Normal/Easy, выбор Easy подтверждён через A. После этого выполнен предусмотренный этой сборкой безопасный выход.** Повтор этой CIA не требуется. [Машинная проверка](hardware-result.json), [наблюдения пользователя](user-observations.json), [текущий gate](../native-game-hid-v0.1.7/release-gate.json).

## Raw HID и игровой ввод

Первое фото: удержание нижней кнопки крестовины, `raw=00000080`, `SDKheld=00000080`, все шесть проверок `Y`. Второе: после отпускания raw и SDKheld равны нулю. `SDKdown=0` во время удержания ожидаем: это фронт нажатия, а не постоянное состояние кнопки. На третьем фото оригинальное меню с выделенной Easy и `ORIGINAL MENU READY / FRAME FAIL`.

Лог содержит все 31 переход HID, без invalid samples и overflow. Preflight зарегистрировал U/D/L/R/A/B и разрешил загрузку через X; до него исходный движок не загружался. Circle Pad в этом аппаратном прогоне отдельно не проверялся.

Каждое игровое событие прослежено по одному id: `HIDRAW → HIDHOST → HIDMAP → HIDCOMPAT ENTER → HIDORIGINAL RETURN → HIDACK`. При нажатии host вызывает штатный DS23 touchscreen adapter и исходный Android pointer callback; выделение меняет сам игровой движок. Проверены и DOWN, и UP pointer events.

| Физическое событие | id | Original ACK | Raw → host | Raw → ACK |
|---|---:|---|---:|---:|
| ↓, Normal → Easy | 22 | frame 4890, selection 2 | 31,817 мс | 413,152 мс |
| ↑, Easy → Normal | 24 | frame 5303, selection 1 | 12,041 мс | 186,743 мс |
| ↓, Normal → Easy | 26 | frame 5481, selection 2 | 28,825 мс | 181,967 мс |
| A, подтверждение Easy | 30 | frame 6362, phase 3 / closing 1 | 433,538 мс | 805,688 мс |

Это интервалы диагностических отметок с файловым IO, а не камера-замер момента видимого изменения. Пользователь сообщил быструю реакцию меню. Для всех четырёх событий `SDKdown` главного цикла уже нулевой; для A нулевой также `SDKheld`. **Физический A длиной около 221 мс всё равно дошёл до оригинального движка через очередь**, несмотря на нулевой SDK snapshot. Это аппаратное доказательство полезности захвата независимо от render polling. Оно не устанавливает задним числом точную причину потери DOWN в 0.1.6.

Максимальный raw sample gap при готовом меню **187,932 мс**, за весь процесс **1537,847 мс**; main sample gap **300843,380 мс**. Номинальные 4 мс collector не гарантированы. Переполнений 0, invalid samples 0, всего 135940 чтений. Исправление работает в полученном испытании; безусловная регистрация любых более коротких физических импульсов не доказана.

B зарегистрирован как отдельные down/up, доставлены оригинальные Android module 600 / key 4; оба callback вернулись. Видимого возврата не было — это ожидаемое поведение первого исходного LayerDifficulty, игнорирующего BACK. Ручной pop меню не добавлялся.

## Подтверждение A и выход

A на frame 6361 получил `original_selection=2` (Easy). После pointer UP исходный движок подтвердил `phase=3, closing=1` на frame 6362. На frame 6363 состояние уже `phase=0, closing=1`: переход продолжался в пределах разрешённых **двух callback после A**. Затем `MENU_ONLY ... tail_complete=6363` запустил штатное завершение. Пользователь оказался в HOME приблизительно через 3 с от A.

Это **предусмотренное завершение menu-only сборки**, подтверждённое логом, а не непредвиденный вылет. Новая игровая сцена в этом кандидате намеренно не запускалась до известных audio NULL/fog ограничений. Успешный ACK не означает появления управляемого Айзека.

Collector joined/freed до native shutdown. Пять оставшихся игровых workers имеют `done=1, kernel_wait=0`, после join записей с entry нет. `IOactive=0`, открытий/закрытий **176/176**, stdio/appdata/dirs 0, `SHUTDOWN live workers=0`, GPU error / failed submits 0. Один shutdown attempt, cleanup complete, safe_exit true, exit.txt и `PROCESS return` присутствуют. HOME → X и START в этом прогоне не проверялись; прежние доказательства остаются отдельными. Независимое измерение освобождения hardware heap/UAF этим логом не выполнялось.

## Почему долго появляется меню

SDK timestamps отделили пользовательское время preflight/фотографирования от исходной игры:

- X / запрос оригинального движка: 88160,843 мс от начала collector.
- Возврат bootstrap/lifecycle initialization: 90808,314 мс, то есть **2,647 с после запроса**.
- Готовность оригинального меню: 647488,289 мс, то есть **559,327 с = 9 мин 19,3 с после запроса**. Это отметка admission состояния, не точный момент фотографии/scanout.
- Самый дорогой `NativeOnDrawFrame 4082`: **300644,235 мс = 5 мин 0,6 с**. Он воспроизводит те же 129 texture allocations, что аппаратный 0.1.6 callback 4132.

В этом одном callback: 1146 glDrawElements, **201 page saves / 166 loads**, 367 CRC над **1069965312 bytes**. `ds15_resident` занимает 222650,207 мс и включает page CRC 50720,571 мс. `ds34_begin_draw` 63161,770 мс, TexImage 14158,776 мс. Записанные GPU queue waits 93,373 мс и VBlank 1361,508 мс не объясняют пяти-минутную паузу. Основная тяжёлая операция — исходная подготовка font/menu atlas с частым обменом страниц текстур и CPU/IO работой. Это не ожидание ввода. Нулевые чтения исходного loader внутри draw не означают отсутствия IO texture pager.

Времена вложены, складывать их нельзя; отдельного чистого IO timer нет. Предыдущий аппаратный draw занимал 297416,915 мс, текущий 300644,235 мс — **ускорения загрузки не получено и не заявляется**. Движок/обязательные операции/GPU не менялись. Наблюдение пользователя «первичная загрузка быстрая, долго жду окно» подтверждено отдельными отметками.

Стабильное оригинальное меню: **23,208 FPS с диагностикой**; средние callback 16,335 мс, present 16,691 мс, diagnostics 7,806 мс. Queue wait 3,106 мс и VBlank 12,417 мс входят в другие интервалы; это не чистое GPU time. Прежний аппаратный результат 23,201 FPS практически тот же.

## Память и изображение

Prod124: normal peak **19816448 bytes**, linear **104635264 / 104857600**, transient headroom **222336 bytes**, kernel commit **126779392 / 130023424**. Donor refusals/runtime failures 0. Запаса linear мало; загрузка первой сцены нуждается в отдельном программном контроле памяти.

**CRC остаётся FAIL**, baseline `ea733050` не менялся; старое расхождение 9231 пиксель не исправлялось этим этапом. Независимо пересчитаны **55 raw/readback CRC пар и 55 полных GX-файлов**, усечённых traces нет. Шесть начальных кадров Normal побайтно равны аппаратному 0.1.6 (`95b893de`). Stable Easy даёт `799656aa`; после UP сохранён Normal frame 5400 с `f49fe214`, он не выдаётся за прежний побайтно идентичный кадр. После подтверждения CRC меняется (`183ba40e`, затем `22d19b9c`). Все значения сохранены честно; CRC не используется для допуска ввода.
