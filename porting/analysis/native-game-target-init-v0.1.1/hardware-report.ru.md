## Почему кнопки не работали

`run()` после600 неуспешных сравнений возвращает−1. Main вызывает `fatal("initialization/frame blocked")`, записывает blocked result, показывает STOPPED и входит в бесконечный SleepThread. В этом пути нет `hidScanInput` и `aptMainLoop`. Поэтому нет обработки START и штатного HOME lifecycle; это fail-stop приложения, **не доказанное зависание PICA или cooperative shutdown**.

`shutdown_game()` не вызван, нет threads-before_pause/after_quiesce/after_join и exit.txt. Поля active_threads/finished_threads0 в blocked JSON — **устаревший main snapshot**, не доказательство завершения потоков. Ресурсы намеренно удерживаются; прежний успешный механизм остановки шести потоков этим запуском ещё не испытывался. Ранее названное ограничение fatal теперь прямо подтверждено симптомом и журналом.

## Следующий минимальный шаг

Сначала в отдельном software варианте проверить выход **при уже воспроизведённом CRC_FAIL**, вызывая существующий cooperative shutdown только из main после возврата callbacks. Frame result должен остаться FAIL, а успешное освобождение ресурсов отмечаться отдельно; не переводить blocked frame в passed. GPU/шейдер/условие CRC и watchdog budget в этом эксперименте не менять. Отрицательный сценарий можно воспроизвести прежним poison без приставки; необходимые resource guards должны запрещать освобождение при незавершённых workers/GPU. Текущий startup fatal для неизвестного состояния не следует массово превращать в выход.

После этого отдельное исследование несовпадения: зафиксировать более ранний аппаратный checkpoint и сопоставимые параметры исходных draws/перехода, сохраняя строгую проверку. Сейчас имеющегося финального raw недостаточно, чтобы выбрать правку GPU, reset между заставками или временную синхронизацию. Эти факторы не смешивать. Новая CIA и новое аппаратное испытание в этом разборе **не создавались/не выполнялись**; старую0.1.1 не повторять.
