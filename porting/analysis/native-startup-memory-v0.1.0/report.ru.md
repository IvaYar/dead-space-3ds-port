# Проверка раннего memory blocker — 31.10.2026

Ветка: `diag/native-startup-memory`. Аппаратный FAIL h2 остаётся действительным: оба экрана чёрные до намеренного A, диагностической папки нет, выключение удержанием Power. Новых аппаратных запусков не было. **Превышение доступной памяти пока не доказано.** Подготовлена отдельная CIA малого startup; игра и GPU backend не изменены.

## Откуда берутся 172 MiB

В `tests/native_game.c` заданы сильные data symbols `__ctru_heap_size = 40*1024*1024`, `__ctru_linear_heap_size = 132*1024*1024`, `__stacksize__ = 256*1024`. Значения прочитаны также непосредственно из PT_LOAD ELF h2: 41943040, 138412032 и 262144 bytes. Они перекрывают weak defaults libctru. Линкер не добавляет ещё одну такую резервацию; RSF/exheader задаёт допустимый профиль, но не эти размеры куч.

128 MiB донорской арены выделяются **внутри** 132 MiB linear heap после начала игрового запуска; прибавлять их к 172 MiB ещё раз неправильно. Донорский ELF, его конструкторы, игровые потоки и GPU-ресурсы создаются после A, а не являются ранней статической BSS этого приложения.

## Какая CIA разобрана

Реальный контейнер `3ds/build-native-game-v0.1.0-h2/native-game.cia`, 336320 bytes, SHA256 `90fb19919c1b132e30fed0936802375d2ccecfdbb7d9c504d5edbef131d35622`. Извлечённый NCCH совпадает с сохранённым h2 CXI/payload; исследован его exheader, а не только текст RSF. Идентичность CIA, установленной пользователем на приставке, отдельно не измерена.

64MB — legacy field; New3DS extended profile указан отдельно. Декларация 178MB не является замером реально полученного лимита на приставке. [Декодированный контейнер](h2-CIA-audit.txt).

## Используемая libctru и порядок выделения

Локальный SDK: пакет **libctru 2.7.0-1** из `toolchain/manifest.json`; `libctru.a` SHA256 `5e72cd24512b57908545e928cf0a1c1affbb8535f97773d7007be8f10f0e02bc`. Получен официальный tag v2.7.0; os.h/env.h побайтно совпали с установленными. Исходники, SHA и URL сохранены отдельно. Из архива SDK извлечён настоящий allocateHeaps.o; его инструкции и связанный ELF h2 подтверждают тот же механизм.

SDK до main вычисляет `remaining = (maxCommit-currentCommit) & ~0xfff`. Сумма явно заданных куч сравнивается с remaining; затем отдельно резервируются normal и linear. Превышение либо отказ ControlMemory ведёт в svcBreak до экранного/SD logger. При двух ненулевых размерах автоматического уменьшения нет. После этого CRT инициализирует службы; `__appInit` также может остановиться до main. [Официальный allocateHeaps.c v2.7.0](https://raw.githubusercontent.com/devkitPro/libctru/v2.7.0/libctru/source/system/allocateHeaps.c), [дизассемблер SDK object](linked-allocateHeaps.asm.txt), [связанный h2 ELF](linked-h2-allocateHeaps.asm.txt).

## Бюджет с уже занятой памятью

Для h2: text+RO+page-rounded(data+BSS) = **520192 bytes**, main stack = **262144**, всего image+stack = **782336**. С дополнительным допуском в одну TLS-страницу получаем **786432 bytes = 0,75 MiB**. Это расчётная модель, а не измерение hardware currentCommit: реальные дополнительные charges и учёт TLS неизвестны.

| Фактический лимит, если он такой | До heap, модель | Останется до heap | Запрос | Остаток после |
|---|---:|---:|---:|---:|
| 178 MiB | 0,75 MiB | 177,25 MiB | 172 MiB | **+5,25 MiB** |
| 124 MiB | 0,75 MiB | 123,25 MiB | 172 MiB | −48,75 MiB |
| 64 MiB | 0,75 MiB | 63,25 MiB | 172 MiB | −108,75 MiB |

При 178 MiB нет доказанного arithmetic overflow бюджета. Если currentCommit превысит 6 MiB, 172 MiB уже не поместятся; ровно 6 MiB допускают сумму без запаса. Достаточный суммарный commit budget сам по себе не гарантирует успех отдельного большого linear allocation. Нельзя утверждать ни доказанный OOM, ни аппаратную совместимость 132 MiB linear только по Azahar.

## Один минимальный подготовленный тест

`tests/native_startup.c` → `3ds/build-native-startup-v0.1.0/startup.cia`, **146880 bytes**, SHA256 `4ae98b7dd2f59df827b9e3f5ad966e4abe2896db538c65be3bf18832ac27fa7c`. Новый Title ID **000400000FDE7200**, HOME **DS Startup Test 0.1.0**.

Кучи 2+2 MiB, stack 256 KiB. Сохранены профиль 178MB, kernel2.44 и настройки доступа h2; изменены только идентификаторы в RSF. Нет donor/оригинальных ресурсов, DS34, Citro3D и PICA submissions. Стандартные SDK gfx/console выводят READY на LCD. До записи SD выполняется первый console framebuffer flush. A ничего не запускает, START завершает main. Диагностика в новой папке `SD:/3ds/ds-native-startup-v0.1.0/run-NNNN/`; прежние логи не затрагиваются.

Безопасная pre-main обёртка читает только SVC memory counters в статические структуры, вызывает неизменённый SDK allocator и повторяет замер. По связанному ELF проверены обе связи: CRT → wrapper → original allocator. Из основного игрового процесса эта обёртка не вызывается: он не пересобирался.

Три последовательных запуска payload, извлечённого из **готовой CIA**, в одном Azahar core/SD: main/READY, START, GSP ReleaseRight и освобождение normal/linear до host unload. Новых memory exceptions/assertions/unmapped accesses не найдено. Каждый цикл дал limit **186646528**, current до heap **409600**, после **4603904**, delta **4194304** bytes. 400 KiB current малого теста совпадают с его image+stack; дополнительная TLS-страница в этом измерении эмулятора не начислена. Поэтому TLS allowance модели h2 не выдаётся за установленный аппаратный charge.

[Три цикла и измерения](../azahar-native-startup-v0.1.0/result.json), [build manifest](../../3ds/build-native-startup-v0.1.0/build-manifest.json), [инструкция](../../3ds/README-native-startup.ru.md). Нет аппаратного PASS и нет гарантии достижения main на устройстве. Протестирован CIA payload, не установка через HOME Menu на настоящей консоли.

READY+START на железе подтвердят малый startup в том же профиле, но не докажут OOM h2: минимальный executable существенно меньше и без игровых зависимостей. Низкий фактический лимит даст конкретный конфликт бюджета. При лимите178 и достаточном расчётном остатке нужно отдельно различить отказ большого linear allocation и службы/gfx/SD; при чёрных экранах малого теста нельзя продолжать слепое уменьшение памяти игры.

## План выделения памяти игры после аппаратного измерения

Это план следующего изменения, **не выполненное исправление игрового процесса**:

1. Снять реальные limit/current в малом startup; затем в отдельном game-bootstrap измерять собственные image/stack/current и результаты каждого выделения до вызова donor. Если лимит64/124, устранить конфликт профиля/загрузки, не сокращать донорскую арену вслепую.
2. Возможный следующий bootstrap сохраняет **40 MiB normal**, имеет **4 MiB SDK linear** для display/GPU pool. Он доходит до READY до большого запроса. После явного начала и проверки remaining отдельно запросить **128 MiB contiguous linear arena** через проверяемый ControlMemory. Общая потребность остаётся **40+4+128=172 MiB**; размер донорской арены и требования движка сохраняются. Это позволит локализовать отказ большого запроса после main, но не снижает итоговую потребность.
3. Большой блок не включать задним числом в инициализированный SDK buddy allocator. Не менять `__ctru_linear_heap_size` после инициализации и не вызывать `__system_allocateHeaps` второй раз. У отдельного блока должны быть свои address/size/owner/free; до передачи его в DS9 проверить выравнивание и совместимость потребителей адресов/кэша. Даже при достаточном total budget его непрерывность требует отдельной проверки.
4. Выделить полную арену и подтвердить все бюджеты/ошибки **до конструкторов, потоков и игрового GPU submit**. При отказе показать точный Result и выйти через START без частично запущенного donor. Не обещать доступные 128 MiB до успешного выделения.
5. Сохранять исполняемый код/RX mappings, trampoline storage, стеки, арену и GPU-буферы до GPU completion и истинного завершения всех шести потоков существующим cooperative safe_exit. Освобождать отдельную арену только после этого; при неполном завершении удерживать ресурсы, не выдавать PASS.
6. После реализации — минимальный native-frame test, точное сравнение с неизменённым GPU baseline и последовательные START/exit cycles. Лишь затем отдельное согласование аппаратного испытания игры.

План 40+4+128 условен: применимость требует проверки собственного фактического бюджета и адресного размещения. Он не решает нехватку общего лимита и сам по себе не доказывает причину прежнего зависания.

## Сохранность и воспроизведение

`tools/audit_native_startup_memory.py` читает ELF globals/exheaders, проверяет модель и результаты трёх циклов, совпадение pinned headers, SDK allocator object и SHA **145 защищённых файлов**. Изменений этих файлов нет: исходники GPU/shader/runtime, main h2, s16 safe_exit, старые builds и исходный ZIP сохранены. [Итог сверки](verification.json), [машинный бюджет](memory-budget.json).

Новые файлы: минимальный entry point, отдельные builder/runner/read-only audit и документы. Нет запуска полного ARM suite, игрового аппаратного теста, push или публикации частных данных. CIA не содержит коммерческих ресурсов.
